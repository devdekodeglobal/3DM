# Security release procedure

These steps are for the reviewed security-audit branch. Local testing does not configure the public Cloudflare project. Do not deploy only the frontend: the API, database migration and frontend verification protocol change together.

1. Back up the target D1 database using your normal protected backup procedure. Export any important existing browser drafts before rollout; old drafts without an account label will be cleared when the secure workspace boundary first opens.
2. Apply `migrations/0001_security.sql` to the target D1 binding before serving the new API. This adds rate-limit, registration-challenge and OAuth-challenge tables without dropping users/designs. Apply it to a separate local D1 database first.
3. Configure a cryptographically random `SECURITY_SECRET` with at least 32 bytes as a Cloudflare secret, plus existing `RESEND_API_KEY`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Never place secrets in VITE_ variables or commit their values. Configure `RESEND_FROM` to an approved sender for delivery beyond provider sandbox recipients. The HMAC key must be stable across instances; changing it expires outstanding codes.
4. Backfill all legacy password records using the bounded `backfillPasswords` helper in `functions/_password-migration.ts`, in a controlled administrative job with access to the intended D1 binding. It uses compare-and-update guards and never needs plaintext passwords. No administrative HTTP endpoint is shipped. Continue until the count of hashes with the old 44-character representation is zero. A successful ordinary login also upgrades an old hash, but dormant records need the backfill for complete at-rest coverage.
5. Review accounts linked with the previous Google-by-email flow. Password login for Google-linked accounts is now disabled. Revoke existing sessions before release after notifying test users: old sessions may predate the corrected linking behavior. This is an operational step, not an automatically executed migration. Investigate unexpected Google subjects before allowing affected accounts back in.
6. Use HTTPS staging and register its exact `/api/auth/google` callback with Google. Confirm fresh/returning Google sign-in, canceled login, password-account collision, PKCE exchange and one-use state. Verify real email delivery, re-registration after delivery failure and code expiry. These provider checks were intentionally left for staging because the user requested local validation only.
7. Install with `pnpm install --frozen-lockfile`, then run `npm test`, `npm run test:workers`, `npm run typecheck:api`, `npm run build` and `pnpm audit`. The Workers test uses a separate in-memory D1 database and mocked outbound services. Confirm the production Workers CPU allowance supports the 600,000-iteration KDF; local wall time is not a measurement of billed production CPU. Use a paid/configured CPU allowance as needed rather than weakening hashes.
8. Deploy the reviewed API and frontend together, then inspect real HTML/API headers. Verify sign-in, cloud save/load/delete, custom GLB/PNG/JPEG/SVG import, two-account ownership, shared-browser sign-out, and account changes across tabs. Check CSP in each supported browser. Third-party Google/decoder endpoints are allowlisted; CSP has no unsafe-inline JavaScript allowance.

Current product budgets: 1 MiB project JSON, 500 total elements including nested walls, 100 m space dimensions, 120-character project names, 10 cloud projects, 25 MiB uncompressed self-contained GLB models and 256 KiB logos. Embedded textures are PNG/JPEG with dimension and pixel budgets. Compressed or externally linked custom models are rejected with a message; trusted built-in models use the existing loader path.

Recovery is still limited: no password-reset feature is included in this release. Do not claim it was implemented or tested. Add a separately reviewed recovery flow before promising self-service password recovery to customers.
